### 整体流程

![agent_zs架构图](E:\WorkSpace\Project\Agent-Zs\docs\agent_zs架构图.png)

**1. API入口(tool.py/task.py)** — 请求从 Java 网关过来，带着可信头(用户ID、租户ID、权限码)。这一层先解析可信头，拿到 `AuthContext`，之后所有节点都基于这个上下文做权限判断，不需要重新鉴权。

**2. 规则路由** — 先看能不能不经过大模型就把请求处理掉。截图里那种"查询库存""创建订单"快捷按钮，点击时本身就带着预设的工具名和参数，直接命中规则路由，**跳过 Planner，直接进入第5步的工具注册中心**。自由输入的文本如果命中关键词表(比如包含"报销""审批"这类词)，同样直接路由，不进大模型。

**3. Planner(唯一的LLM节点)** — 只有规则路由匹配不上的复杂/长尾请求才会走到这里。它把用户的自然语言转成结构化的任务计划(一组 `steps`，每步带工具名、入参、依赖关系)。它只负责"理解和规划"，不负责"要不要确认""要不要重试"这类判断——那些判断权在后面的确定性节点手里。

**4. Executor执行器** — 拿到规则路由或 Planner 给出的结果后，按依赖关系逐步调度工具执行。它是纯代码逻辑：该走哪个分支、失败了要不要重试、重试几次，全部按预先写好的规则判断(比如超时重试N次、参数错误直接终止)，不再问模型的意见。

**5. 工具注册中心** — Executor 真正调用工具之前，先来这里查这个工具的静态配置：风险等级、是否需要人工确认、超时时间、重试策略。这些配置是注册工具时写死的，Executor 只是读取，不会因为某次对话内容不同就临时改变判断标准。

**6. ERP适配层** — 如果这一步调的是 ERP 相关工具(比如建报销单)，会走到这个专门的适配层，负责生成/校验幂等键，调用 ERP 现有 API，并在断线恢复场景下做"状态核对"(查ERP侧真实状态，而不是盲目重试)。

**7. Checkpointer——你问的这个**：

它做的事情是"把 LangGraph 图当前执行到哪一步、每一步的输入输出是什么，完整存下来"，具体设计是这样的：

- LangGraph 本身定义了一个 `Checkpointer` 接口，默认实现是存内存或本地文件，**但企业场景要换成自定义实现，把状态写进 MySQL `agent_zs` 库的 `agent_task`/`agent_task_step` 表**，而不是用默认的临时存储
- 每次图执行完一个节点(比如 Executor 调完一个工具),就触发一次 checkpoint 写入，`thread_id` 用 `task_id` 标识，checkpoint 内容包含"当前在哪个节点、已经产出的中间结果、下一步该走哪"
- **恢复时**：如果任务因为网络断开、服务重启中断了，重新发起请求时带上同一个 `task_id`，LangGraph 会先去 Checkpointer 读最后一次存档，**从那个节点继续跑**，而不是把整个计划重新执行一遍——这就是它能省掉你之前要求的"断点恢复"里"图执行到哪一步"这部分自研工作量的原因
- **人工确认场景**：走到 ERP 建单这类高风险步骤时，图会调用 LangGraph 的 `interrupt()`，此时 Checkpointer 会存一个"暂停等待确认"的检查点，图执行真正挂起，直到用户在前端点了确认、调用确认接口，图才从这个检查点恢复继续往下走
- **要划清的边界**：Checkpointer 只负责"图执行到哪一步"这个技术层面的续跑，**它不知道、也不负责判断"ERP那边单据到底建成功没有"**——这部分是第6步 ERP适配层里的幂等键+状态核对在管，两者配合起来才是完整的断点恢复机制,不是 Checkpointer 一个人能顶的

**8. MySQL agent_zs库** — 最终落地的物理存储，`agent_task`/`agent_task_step`(Checkpointer用)、`idempotency_record`/`erp_order_mapping`(ERP适配层用)都在这里，各自独立的表，互不覆盖。
