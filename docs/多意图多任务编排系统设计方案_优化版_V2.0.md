# 多意图多任务编排系统设计方案（优化版）

> 版本：V2.0  
> 适用场景：企业级 Agent、ERP/WMS/HR 智能助手、RAG + Tool Calling、多意图任务编排、审批流、复杂业务自动化  
> 核心目标：将自然语言请求转换为可验证、可恢复、可审计、可重规划的任务执行流程，并支持 Tool、Agent、Human Task 的统一编排。

---

# 1. 背景与目标

在企业级 Agent 应用中，用户的一条 Query 经常不仅包含一个简单问题，而是同时包含多个意图、多个任务以及任务之间的依赖关系。

例如：

```text
帮我查一下张三有没有报销权限，如果有，就按照公司差旅标准生成一份上海出差报销单。
```

这个请求至少包含：

```text
查询用户信息
    ↓
查询报销权限
    ↓
查询差旅标准
    ↓
生成报销单
    ↓
用户确认
    ↓
提交审批
```

再例如：

```text
帮我安排下周去上海出差，查天气、机票和酒店，如果跨周末，再推荐几个景点。
```

可以拆解为：

```text
                 ┌→ 查询天气 ─────────────┐
用户请求 → 任务规划 ├→ 查询机票 ─────────────┤
                 ├→ 查询酒店 ─────────────┤→ 综合结果
                 └→ 判断是否跨周末 → 推荐景点 ┘
```

因此，一个企业级 Agent 系统不能只依赖：

```text
用户问题
   ↓
LLM
   ↓
直接调用一个工具
```

而需要构建一套完整的：

```text
理解 → 规划 → 校验 → 编排 → 执行 → 观察 → 重规划 → 聚合
```

的任务运行体系。

## 1.1 当前常见问题

如果每个业务场景都单独编写一套业务流程，会导致：

- 代码难以复用；
- 新场景接入成本高；
- 每个业务都重复实现重试、超时、失败降级；
- 多任务之间的依赖关系难以维护；
- 无法统一支持并行任务；
- 用户确认、审批、授权逻辑分散；
- 服务重启后任务状态无法恢复；
- 复杂 Agent 行为无法追踪；
- Planner 生成错误任务计划时可能直接进入执行阶段；
- 高风险 Tool 可能被错误调用；
- 出错后通常只能整体失败，无法动态调整执行计划。

# 2. 设计目标

本方案目标是构建一个：

```text
业务无关
可扩展
可恢复
可观测
可审计
可控制
可重规划
```

的通用多任务 Agent 编排框架。

业务方接入新业务时，原则上只需要：

```text
注册 Tool
+
定义 Tool Schema
+
配置权限与风险等级
+
补充少量 Prompt / Few-shot
```

而无需重新编写一整套编排逻辑。

核心目标包括：

1. 支持单意图和多意图请求；
2. 支持简单请求快速路由；
3. 支持复杂请求自动 Planning；
4. 支持串行、并行、条件、分支任务；
5. 支持 Tool、Agent、Human Task；
6. 支持任务状态持久化；
7. 支持失败重试和降级；
8. 支持幂等与重复调用保护；
9. 支持用户确认和人工审批；
10. 支持权限控制；
11. 支持动态 Replan；
12. 支持全链路 Trace；
13. 支持任务级审计；
14. 支持 Plan 回放；
15. 支持执行过程恢复；
16. 降低 LLM 幻觉对执行层的影响。

# 4.2 Query Understanding Layer

原本的 Intent & Slot Layer 可以进一步升级为 Query Understanding。

不要只判断：

```text
单意图 / 多意图
```

建议输出：

```python
class QueryUnderstandingResult:
    raw_query: str

    intents: list[str]
    entities: dict
    slots: dict
    constraints: dict
    goals: list[str]

    missing_required_slots: list[str]

    risk_level: str

    requires_planning: bool

    clarification_question: str | None
```

示例：

用户：

```text
帮我订明天下午北京到上海的高铁，预算500元以内。
```

解析：

```json
{
  "intents": [
    "search_train",
    "book_train"
  ],
  "entities": {
    "departure": "北京",
    "destination": "上海"
  },
  "slots": {
    "date": "tomorrow",
    "time_range": "afternoon"
  },
  "constraints": {
    "max_price": 500
  },
  "goals": [
    "找到符合预算的高铁",
    "完成预订"
  ],
  "risk_level": "medium",
  "requires_planning": true
}
```

## 为什么使用 requires_planning

不要使用：

```text
is_multi_intent
```

作为 Planner 是否执行的唯一依据。

因为：

```text
查询北京天气
```

虽然是单意图，但非常简单：

```text
Direct Tool
```

而：

```text
分析这份合同有哪些风险
```

虽然可能属于单一业务意图，但内部可能包含：

```text
解析合同
→ 提取条款
→ RAG 查询法规
→ 风险识别
→ 风险评级
→ 汇总
```

因此真正需要判断的是：

```text
任务复杂度
```

而不是单纯的意图数量。

# 4.3 Complexity Router

新增 Complexity Router。

职责：

```text
判断是否需要 Planning
```

推荐三级：

```text
Level 0：直接回答
Level 1：单 Tool
Level 2：复杂 Planning
```

示例：

| 请求 | 路由 |
|---|---|
| 你好 | LLM |
| 北京天气 | Direct Tool |
| 查订单 10001 | Direct Tool |
| 查询张三报销权限 | Direct Tool |
| 查权限后生成报销单 | Planner |
| 安排完整出差 | Planner |
| 分析经营数据并生成报告 | Planner |

伪代码：

```python
if query.requires_planning:
    return planner.plan(query)

if query.tool_candidate:
    return direct_tool_call()

return llm_response()
```

优点：

```text
减少 Planner 调用
降低 Token
降低延迟
提升简单问题响应速度
```

# 4.4 Tool Registry

Tool Registry 是整个架构最关键的基础设施之一。

建议从 ToolSpec 升级到 Capability ToolSpec。

```python
@dataclass
class ToolSpec:
    name: str
    version: str

    description: str
    tags: list[str]
    capability: str

    input_schema: dict
    output_schema: dict

    timeout_ms: int

    is_idempotent: bool
    side_effect: bool

    requires_confirmation: bool
    required_permissions: list[str]

    risk_level: str

    fallback_strategy: str

    retry_policy: dict

    concurrency_limit: int

    compensation_tool: str | None

    estimated_latency_ms: int | None
    estimated_cost: float | None
```

示例：

```python
ToolSpec(
    name="submit_expense_report",
    version="1.0",

    description="提交员工报销单",
    tags=["expense", "erp"],
    capability="expense.submit",

    input_schema={
        "report_id": "str"
    },

    output_schema={
        "approval_id": "str",
        "status": "str"
    },

    timeout_ms=5000,

    is_idempotent=False,
    side_effect=True,

    requires_confirmation=True,

    required_permissions=[
        "expense.submit"
    ],

    risk_level="high",

    fallback_strategy="BLOCK",

    retry_policy={
        "max_attempts": 1
    },

    concurrency_limit=10,

    compensation_tool=None
)
```

# 4.5 Tool Semantic Schema

仅有 JSON Type 还不够。

例如：

```text
temperature: number
amount: number
```

都是 number，但不能互相引用。

因此建议加入：

```text
semantic_type
```

示例：

```json
{
  "amount": {
    "type": "number",
    "semantic_type": "currency:CNY"
  },
  "temperature": {
    "type": "number",
    "semantic_type": "temperature:celsius"
  }
}
```

这样可以避免：

```text
Planner 将温度字段作为付款金额
```

类似的 Semantic Type 可以包括：

```text
user_id
order_id
flight_id
hotel_id
currency:CNY
currency:USD
date
datetime
email
permission_level
department_id
```

# 5. Plan IR

Plan IR 是 LLM 与执行引擎之间的中间表示。

示例：

```json
{
  "goal": "生成并提交报销单",
  "steps": [
    {
      "id": "step_1",
      "action": "query_user_permission",
      "inputs": {
        "user_id": "$context.user_id"
      }
    },
    {
      "id": "step_2",
      "action": "query_expense_policy",
      "inputs": {
        "city": "上海"
      }
    },
    {
      "id": "step_3",
      "action": "generate_expense_report",
      "after": [
        "step_1",
        "step_2"
      ]
    },
    {
      "id": "step_4",
      "action": "submit_expense_report",
      "after": [
        "step_3"
      ],
      "requires_confirmation": true
    }
  ]
}
```

Plan IR 的优势：

```text
LLM 不直接控制执行器
```

LLM 只负责表达：

```text
我要做什么
任务之间是什么关系
```

真正的：

```text
Task ID
Timeout
Retry
Permission
Risk
Concurrency
Execution Type
```

由代码生成。

# 6. Plan Validator

Planner 输出后不能直接执行。

必须经过：

```text
Plan Validator
```

至少进行以下校验：

## 6.1 Schema Validation

检查：

```text
字段是否合法
类型是否合法
必填字段是否存在
```

---

## 6.2 Tool Exists Validation

检查 Planner 使用的 Tool：

```text
是否真实存在于 Tool Registry
```

禁止 LLM 自己创造 Tool：

```text
transfer_money_v2
delete_user_data
```

如果 Registry 没有，就不能执行。

---

## 6.3 Dependency Validation

检查：

```text
depends_on 引用是否存在
```

例如：

```text
task_4 depends_on task_99
```

应该直接拒绝。

---

## 6.4 Cycle Detection

检查 DAG 是否存在循环：

```text
task1 → task2
 ↑       ↓
 └────task3
```

推荐：

```text
Topological Sort
```

进行环检测。

---

## 6.5 Input / Output Validation

检查：

```text
前置任务输出
        ↓
后置任务输入
```

是否兼容。

例如：

```text
query_permission.output.level
        ↓
generate_report.input.permission_level
```

需要：

```text
Type Compatible
Semantic Compatible
```

---

## 6.6 Permission Validation

即使 Planner 选择了 Tool，也必须检查：

```text
当前用户是否拥有调用权限
```

例如：

```text
员工
  ↓
delete_employee
```

即使 Planner 生成了这个任务，也应该被 Policy Engine 阻止。

---

## 6.7 Risk Validation

例如：

```text
查询天气 → LOW
查询工资 → MEDIUM
生成报销单 → MEDIUM
提交报销 → HIGH
转账付款 → CRITICAL
```

对于高风险任务：

```text
强制人工确认
```

不能只依赖 LLM 输出：

```json
"requires_confirmation": true
```

而应该由：

```text
ToolSpec
+
Policy Engine
```

强制决定。

# 7. Plan Compiler

Plan Compiler 将 Plan IR 转换为真正的 Workflow。

例如：

LLM：

```json
{
  "id": "step_4",
  "action": "submit_expense_report"
}
```

Compiler 根据 Tool Registry 自动补充：

```json
{
  "task_id": "task_4",

  "tool": "submit_expense_report",

  "timeout_ms": 5000,

  "retry": {
    "max_attempts": 1
  },

  "requires_confirmation": true,

  "risk_level": "high",

  "required_permissions": [
    "expense.submit"
  ],

  "depends_on": [
    "task_3"
  ]
}
```

从而实现：

```text
LLM负责规划
程序负责约束
```

这是整个架构安全性的核心设计之一。

# 8. Workflow Runtime

Workflow Runtime 不应该只是一个简单 DAG Executor。

建议使用：

```text
DAG

State Machine
```

共同驱动任务。

# 9. Task State Machine

推荐状态：

```text
PENDING
   ↓
READY
   ↓
RUNNING
   ├── SUCCESS
   ├── FAILED
   ├── RETRYING
   ├── WAITING_CONFIRMATION
   ├── WAITING_APPROVAL
   ├── WAITING_INPUT
   ├── SKIPPED
   ├── CANCELLED
   └── TIMEOUT
```

定义：

```python
class TaskStatus(Enum):
    PENDING = "pending"
    READY = "ready"
    RUNNING = "running"

    SUCCESS = "success"

    FAILED = "failed"
    RETRYING = "retrying"

    WAITING_CONFIRMATION = "waiting_confirmation"
    WAITING_APPROVAL = "waiting_approval"
    WAITING_INPUT = "waiting_input"

    SKIPPED = "skipped"
    CANCELLED = "cancelled"
    TIMEOUT = "timeout"
```

# 10. Task Runtime State

不要只维护：

```python
results = {}
```

推荐：

```python
@dataclass
class TaskRuntimeState:
    task_id: str

    status: TaskStatus

    input: dict | None
    output: dict | None

    error: str | None

    retry_count: int

    started_at: datetime | None
    finished_at: datetime | None

    waiting_reason: str | None
```

依赖判断：

```python
def deps_satisfied(task, states):
    return all(
        states[dep].status == TaskStatus.SUCCESS
        for dep in task.depends_on
    )
```

这样：

```text
WAITING_CONFIRMATION
FAILED
TIMEOUT
```

都不会被错误认为已经满足依赖。

# 11. DAG Scheduler

调度器每轮寻找：

```text
READY TASK
```

然后并行执行。

基本流程：

```text
读取 Workflow State
      ↓
找到依赖满足的任务
      ↓
READY
      ↓
执行并行 Batch
      ↓
更新 Task State
      ↓
持久化
      ↓
继续调度
```

伪代码：

```python
while workflow_not_finished:

    ready_tasks = find_ready_tasks()

    if not ready_tasks:
        if has_waiting_human_task():
            pause_workflow()
            return

        if has_deadlock():
            raise WorkflowDeadlockError()

    results = await asyncio.gather(
        *[
            execute_task(task)
            for task in ready_tasks
        ]
    )

    persist_states(results)
```

# 12. Retry Engine

原来的：

```text
BLOCK
RETRY
SKIP
```

策略建议继续保留，但 RETRY 要真正实现。

推荐：

```python
@dataclass
class RetryPolicy:
    max_attempts: int = 3

    initial_delay_ms: int = 500

    max_delay_ms: int = 5000

    backoff_factor: float = 2.0

    retry_on: list[str] = None
```

推荐：

```text
Exponential Backoff
```

例如：

```text
第1次失败
 ↓
500ms
 ↓
第2次失败
 ↓
1000ms
 ↓
第3次失败
 ↓
2000ms
```

适合重试：

```text
HTTP 429
HTTP 502
HTTP 503
Network Timeout
Temporary DB Error
```

不建议重试：

```text
HTTP 400
Schema Error
Permission Denied
Insufficient Balance
Business Validation Failed
```

# 13. Idempotency

对于：

```text
查询天气
查询订单
搜索酒店
```

重复执行影响不大。

但是：

```text
支付
提交审批
创建订单
发送邮件
创建用户
```

可能产生副作用。

所以必须支持：

```text
Idempotency Key
```

推荐：

```text
workflow_id
+
task_id
+
business_key
```

例如：

```text
wf_10001:task_4:expense_90001
```

服务端执行前先检查：

```text
该 Idempotency Key 是否已经成功执行过
```

避免因为：

```text
网络超时
重试
服务重启
```

导致重复扣款或者重复提交。

# 14. Human-in-the-loop

企业级 Agent 不建议只支持：

```text
requires_confirmation
```

应抽象为：

```text
Human Task
```

支持：

```text
WAITING_CONFIRMATION
WAITING_APPROVAL
WAITING_INPUT
WAITING_AUTHORIZATION
```

---

## 14.1 用户确认

例如：

```text
AI：
```

# 36. Execution Engine 伪代码

```python
class WorkflowRuntime:

    async def run(self, workflow_id):

        workflow = self.store.load(workflow_id)

        while True:

            if workflow.status in (
                "SUCCESS",
                "FAILED",
                "CANCELLED",
            ):
                return workflow

            ready_tasks = self.scheduler.find_ready(workflow)

            if not ready_tasks:

                if workflow.has_waiting_task():
                    workflow.status = "SUSPENDED"
                    self.store.save(workflow)
                    return workflow

                raise WorkflowDeadlockError()

            results = await self.executor.execute_batch(
                ready_tasks
            )

            for result in results:
                self.state_manager.apply(result)

            self.store.save(workflow)

            if self.replan_policy.should_replan(workflow):

                workflow = await self.replanner.replan(
                    workflow
                )

                self.store.save(workflow)
```

# 39. Failure Strategy

建议：

```text
BLOCK
RETRY
SKIP
REPLAN
COMPENSATE
```

比原先三级更完整。

解释：

| Strategy | 说明 |
|---|---|
| BLOCK | 失败则终止 |
| RETRY | 自动重试 |
| SKIP | 跳过继续 |
| REPLAN | 重新规划 |
| COMPENSATE | 执行补偿 |

例如：

```text
天气失败
→ SKIP

ERP权限查询失败
→ BLOCK

Flight API 503
→ RETRY

没有符合预算的航班
→ REPLAN

酒店已订但机票失败
→ COMPENSATE
```

# 48. 最终结论

这套架构的关键不是：

```text
让 LLM 会调用很多 Tool
```

而是建立：

```text
一个安全、可靠、可恢复的任务运行时
```

推荐核心思想：

```text
LLM负责：

理解
规划
推理
重新规划

程序负责：

约束
校验
权限
执行
状态
重试
恢复
审计
```

也就是：

```text
LLM = Brain

Workflow Runtime = Nervous System

Tool = Hands

Policy Engine = Safety System

Workflow Store = Memory

Observability = Monitoring System
```

最终达到：

```text
自然语言
    ↓
任务理解
    ↓
计划生成
    ↓
计划验证
    ↓
受控执行
    ↓
动态调整
    ↓
可靠完成
```

这才是适合企业级 Agent、多意图、多任务编排系统长期演进的总体方向。
