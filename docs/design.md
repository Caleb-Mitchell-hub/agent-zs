## Problem Statement

为一个现有 ERP 系统（PC端 + 微信小程序端）构建一个 agent 模块，让业务人员用自然语言替代"打开多个系统、导出Excel、手动拼数据、再录入单据"的日常操作链条。系统需要在 Linux 上以 Docker 容器方式部署，作为 ERP 的嵌入式模块运行。

核心能力需求：数据库查询、报表生成、数据生成、RAG 知识检索、创建单据、LLM 推理。

## Demand Evidence

- 有**明确的使用者**在等这个系统上线，不是假设的需求
- 使用者目前的方案是手工 + 多个工具拼凑，每周浪费数小时
- 需求方清楚具体的**人和场景**，不仅仅是角色分类

## Status Quo

使用者当前的工作流：手动在多个系统间切换 → 导出数据到 Excel → 手工 VLOOKUP/透视表 → 生成报表 → 在另一个系统手工录入单据。这是一个高摩擦、易出错、耗时数小时的日常流程。

## Target User & Narrowest Wedge

**目标用户：** ERP 系统中需要频繁查数据、出报表、创建单据的业务人员。他们通过 PC 端和微信小程序端访问系统。

**最窄切入点（修订后）：** 自然语言查询数据库 → 自动生成可视化报表。这是使用者日常最高频的痛感操作——单人即可闭环，不依赖写操作。

**第二阶段：** 接入单据创建（写操作），独立的 agent 和权限边界。

**第三阶段：** RAG 知识检索、数据生成等扩展能力。

## Constraints

| 约束 | 详情 |
|------|------|
| 部署环境 | Linux + Docker 容器化 |
| 嵌入目标 | 现有 ERP 系统，PC 端 + 微信小程序端 |
| 交付形式 | API 服务，ERP 前后端通过 API 调用 |
| 安全要求 | 读写操作需分离 —— 不同的 agent、不同的 DB 权限、不同的审计链路 |
| 技术栈偏好 | Agent 框架待定；避免过度引入重型框架 |
| 微信小程序 | 需要 HTTP API（不支持 WebSocket 长连接用于流式输出时需降级处理） |

## Premises

1. **能力 ≠ Agent。** 数据生成、报表生成、数据库查询、创建单据本质上是工具（tool/function call），不是独立的 agent。LLM 是推理引擎，RAG 是基础设施。真正的问题是：用几个 agent、如何分配工具。

2. **渐进交付。** 不追求六个能力同时上线。第一阶段只做 NL→SQL→报表（读操作），验证后再加写操作和 RAG。

3. **读写分离。** 第二意见指出：创建单据是写操作，涉及不可逆的业务变更。它和查询/报表/RAG 这些读操作必须从架构层面分开——不是因为 LLM 技术约束，而是因为权限模型和审计链路天然不同。读写 agent 各自拥有独立的 DB 凭证和工具集。

4. **先单后多（修订版）。** 读操作内部先用一个 agent 挂载多个工具（query_tool, report_tool, rag_tool）。只有出现上下文污染或工具选择退化时才拆分读 agent。写操作从一开始就是独立 agent。

5. **嵌入而非独立。** 这个系统不是一个独立产品，而是 ERP 的一个模块。认证、权限、审计、UI 框架全部复用 ERP 现有基础设施。

## Cross-Model Perspective

> 独立 Claude 子 agent 冷读（未见过对话历史）的核心发现：

**最强版本：** "这不是一个 agent 平台，这是一个企业内部系统的自然语言操作层——让业务人员用一句话替代'打开三个系统、导出Excel、写VLOOKUP、再手动录入单据'的日常链条。最强的版本不是六个功能，而是**一个功能做到零摩擦**：使用者说完一句话，结果已经在ta们手里。"

**最危险的信号：** Q5——跟使用者聊过但从未静默观察。这是整个对话里最危险的信息缺口。人们口头描述自己工作流程时的准确度极低——会省略"太明显不值一提"的步骤（往往是核心痛点），会美化操作路径，会忘记已经肌肉记忆的 workaround。

**挑战前提3（读写分离）：** "创建单据是写操作，涉及业务状态的不可逆变更。把它和数据库查询、报表生成放在同一个 agent 里，意味着这个 agent 同时拥有读取敏感数据和修改业务记录的权限。在企业内部系统中，这不是技术约束，而是安全边界问题。" **→ 已采纳，写入前提3。**

**48小时原型建议：** 只做 NL→SQL→可视化。Python FastAPI + Anthropic SDK + tool use。不用任何 agent 框架。找一个真实使用者对着原型用自然语言查数据，5分钟能完成日常查询任务就算成功。

## Approaches Considered

### Approach A: 单体服务 + 内部读写分组（最小可行）

**Summary:** 一个 Docker 容器，一个 FastAPI 服务。内部按工具分组隔离读写——读工具（query/report/RAG）和写工具（create_document）在同一进程但权限分层。

| 维度 | 评估 |
|------|------|
| Effort | S（2-3天原型） |
| Risk | 中 —— 安全隔离靠代码约定而非基础设施 |
| Pros | 最快交付，最低运维复杂度，一个服务搞定所有 |
| Cons | 读写的安全边界依赖代码审查而非架构强制；违反前提3 |

### Approach B: 读写双 Agent + API Gateway（理想架构）✅ 选定

**Summary:** 两个独立 Docker 容器——Read Agent（只读 DB 权限，挂载 query_tool/report_tool/rag_tool）和 Write Agent（读写 DB 权限 + 审计日志，挂载 create_document_tool）。API Gateway 做路由和认证。ER P 现有认证层前置。共享 LLM 实例（或各自独立，按需扩展）。

| 维度 | 评估 |
|------|------|
| Effort | M（1-2周原型） |
| Risk | 低 —— 基础设施级安全隔离 |
| Pros | 读写权限天然分离；审计链路清晰；可独立扩缩容；每个 agent 的 system prompt 和工具集小而聚焦 |
| Cons | 两个服务增加运维复杂度；API Gateway 是新增组件；微信小程序端的流式响应需要 SSE/轮询降级 |

### Approach C: Agent-as-Plugin —— 嵌入 ERP 现有架构（侧翼方案）

**Summary:** 不建独立 agent 服务，LLM 作为 ERP 的"推理引擎"直接调用 ERP 现有 API。考虑过但放弃——紧耦合 ERP 难以独立测试和演进，与"agent 作为独立可部署模块"的约束冲突。

## Recommended Approach

**选择方案 B（读写双 Agent + API Gateway）。**

理由：
1. 满足前提3（读写分离）—— 从架构层面而非代码约定层面实现安全隔离
2. 与 ERP 嵌入模式天然匹配 —— API Gateway 对接 ERP 现有认证，两个 agent 各自作为独立服务
3. 渐进交付路径清晰 —— 先上线 Read Agent（最大痛点），Write Agent 独立开发、独立上线
4. PC 端和微信小程序端都通过 HTTP API 访问，架构统一
5. 未来如果需要拆分读 agent 内部（如 RAG 独立），架构已预留扩展空间

**实施路径：**

```
Week 0: NL-to-SQL 可行性验证（先于任何代码）
  → 对真实目标 schema 做 3 个代表性查询
  → 验证：LLM + schema摘要 能否生成正确 SQL
  → 如果 >2 个失败 → 重新评估方案（语义层 / 查询模板 / 问题库）

Phase 1 (Week 1-2): Read Agent 原型
  → NL→SQL→可视化，10个真实查询E2E跑通
  → 找真实使用者静默观察测试

Phase 2 (Week 3-4): Write Agent + API Gateway
  → 单据创建 agent，独立权限和审计
  → Gateway 对接 ERP 认证

Phase 3 (Week 5+): RAG + 数据生成
  → 扩展现有 agent 工具集
  → 知识库对接
```

**技术选型建议：**
- 后端：Python FastAPI（轻量、异步、Docker 友好）
- LLM 调用：Anthropic SDK / OpenAI SDK（tool use 原生支持）
- 数据库连接：SQLAlchemy + 目标 DB 驱动
- 容器化：Docker Compose（3个服务：read-agent, write-agent, api-gateway）
- 不引入 LangChain/CrewAI 等重型框架 —— 第一阶段不需要
- 微信小程序流式输出：使用 SSE 或分段轮询（小程序不支持 WebSocket 流式）

## API Contracts (Phase 1)

### Read Agent — `/api/v1/query`

**Method:** `POST`
**Auth:** Bearer token（由 ERP 认证层签发，Gateway 验证）

**Request:**
```json
{
  "question": "上个月销售额最高的10个客户是哪些？",
  "context": { "user_id": "u_123", "role": "sales_manager" }
}
```

**Response (成功):**
```json
{
  "status": "ok",
  "answer": "上个月销售额前10的客户如下：...",
  "artifact": {
    "type": "table",
    "columns": ["客户名称", "销售额", "订单数"],
    "rows": [["客户A", 123400, 56], ...]
  }
}
```

**Response (需要澄清):**
```json
{
  "status": "clarify",
  "question": "你是指'销售额'按含税还是不含税计算？",
  "options": ["含税", "不含税"]
}
```

**Response (错误):**
```json
{
  "status": "error",
  "code": "QUERY_TIMEOUT | INVALID_SQL | LLM_UNAVAILABLE | AMBIGUOUS_INPUT",
  "message": "查询超时，请缩小时间范围后重试"
}
```

### Read Agent — `/api/v1/report`

**Method:** `POST`
**Auth:** Bearer token

**Request:**
```json
{
  "question": "生成本月销售趋势图",
  "context": { "user_id": "u_123" }
}
```

**Response:**
```json
{
  "status": "ok",
  "answer": "已生成本月销售趋势图：",
  "artifact": {
    "type": "chart",
    "chart_type": "line",

```

## NL-to-SQL Schema Strategy

ERP 数据库可能包含数百张表，直接把完整 DDL 塞进 system prompt 不可行。策略如下：

**初始方案（Phase 1）：**
1. **Schema 摘要**：从目标数据库中提取表名 + 列名 + 注释（不含数据），生成约 2-5K token 的结构化摘要
2. **按需检索**：LLM 先根据用户问题选择相关表（一次 tool call），然后用 `schema_tool(table_names: [...]）` 只获取这些表的完整 DDL
3. **SQL 沙箱**：生成的 SQL 在只读副本上执行；设置 `statement_timeout = 10s`；禁止 `DROP/ALTER/TRUNCATE`（即使只读权限也应加这一层防御）
4. **Schema 刷新**：每次部署时重新生成 schema 摘要；变更频繁时可用定时任务（每小时）

**后续演进（Phase 2+）：**
- 引入语义层：预定义常用查询模板，LLM 做意图分类 + 参数提取，而非每次生成 SQL
- 建立"黄金查询集"：收集真实用户的高频问题 → 人工标注正确 SQL → 作为 few-shot 示例和回归测试

## Failure Modes

| 故障场景 | 用户看到什么 | 系统怎么做 |
|---------|------------|-----------|
| LLM API 不可用 | "AI 服务暂时不可用，请稍后重试" + 错误码 `LLM_UNAVAILABLE` | 返回 503；上层可配置重试（最多 3 次，指数退避） |
| 生成的 SQL 执行超时 | "查询超时，请尝试缩小查询范围" + `QUERY_TIMEOUT` | `statement_timeout` 限制；提示用户加时间范围或简化条件 |
| 用户输入模糊 | 系统反问澄清（如"你是指含税还是不含税？"） | 返回 `status: "clarify"` + 2-4 个选项；最多反问 2 轮 |
| 微信小程序网络中断 | SSE 流断开；小程序端自动重连或切换轮询 | 后端保留最近 N 条消息，支持断点续传（Last-Event-ID） |
| 数据库只读副本不可用 | "查询服务暂时不可用" + `DB_UNAVAILABLE` | Read Agent 健康检查失败 → Gateway 熔断 → 返回 503 |
| 写操作冲突（Phase 2） | "单据创建失败，请检查后重试" | 乐观锁 / 幂等键；审计日志记录每次写操作的完整 payload |

## Tool Definitions

每个 tool 的职责、输入、输出：

| Tool | Agent | 职责 | 输入 | 输出 |
|------|-------|------|------|------|
| `query_tool` | Read Agent | 将自然语言转为 SQL，在只读副本上执行，返回结构化数据 | `sql: string` | `{columns: [...], rows: [[...], ...], row_count: int}` |
| `report_tool` | Read Agent | 将自然语言查询转为可视化图表配置 | `query: string, chart_type: string \| null` | `{type: "chart", chart_type: "line"\|"bar"\|"pie", config: {...echarts/json...}}` |
| `rag_tool` | Read Agent | 从知识库检索相关内容（操作手册、业务规则等） | `query: string, top_k: int (default 5)` | `{chunks: [{content, source, score}, ...]}` |
| `gen_tool` | Read Agent | 生成测试数据或模拟数据集（Phase 3） | `schema_desc: string, row_count: int` | `{columns: [...], rows: [[...], ...]}` |
| `create_document_tool` | Write Agent | 在 ERP 系统中创建单据，带审计记录 | `doc_type: string, payload: {...}, idempotency_key: string` | `{doc_id: string, status: "created"\|"pending_approval"}` |

> 注：`gen_tool` 在架构图中出现在 Read Agent 是因为数据生成本身不修改生产数据——它在只读副本或独立 schema 中生成数据集。如果后续发现需要写入，移入 Write Agent。

## API Gateway Scope

Gateway 是一个**薄反向代理**，不是独立的认证服务：

- **它做什么：** 验证 ERP 认证层签发的 token（JWT 签名校验 / Session 有效性检查），将合法请求路由到 Read Agent 或 Write Agent，限流（per-user rate limiting）
- **它不做什么：** 不签发 token、不管理用户/角色/权限（这些全部复用 ERP 现有认证层）、不存储业务数据
- **信任边界：** Gateway 在 ERP 信任域内部，和 ERP 现有服务部署在同一网络；Gateway 本身不持有数据库凭证

## Open Questions

1. ERP 现有的认证机制是什么？API Gateway 对接方式？（JWT / Session / OAuth2？）
2. 创建单据是否需要审批流程？agent 生成的单据谁来签？
3. **微信小程序 SSE 兼容性（高风险）：** `wx.request` API 没有原生 EventSource 支持，chunked transfer encoding 在各平台表现不一致。是否已在目标小程序版本上测试过 SSE？如果不可靠，是否接受纯轮询模式（2-3 秒延迟）？
4. 目标数据库类型和版本？（MySQL / PostgreSQL / SQL Server？）
5. RAG 的知识库内容是什么？（操作手册 / 业务规则 / 历史单据？）

## The Assignment

**在写任何代码之前，做一件事：找一个真实使用者，坐在ta旁边看ta干30分钟活。不说话，不帮忙，只观察。**

观察重点：
1. ta 在哪些步骤停顿、重复、出错？
2. ta 打开了哪些系统/窗口？切换了几次？
3. ta 有没有用快捷键、复制粘贴、或任何"太明显不值一提"的 workaround？

这些观察会直接决定 Read Agent 的第一个 tool 应该长什么样。如果跳过这一步，你就是在为想象中的人设计系统。

### 测试验证示例

**查询：** "统计每个仓库的库存总数量"
**生成 SQL：**
```sql
SELECT w.id AS warehouse_id, w.warehouse_name, COALESCE(SUM(i.quantity), 0) AS total_quantity
FROM warehouse w
LEFT JOIN inventory i ON w.id = i.warehouse_id
GROUP BY w.id, w.warehouse_name
ORDER BY w.id;
```
**结果：** 北京中心仓 2872 件，上海分仓5 4500 件，广州分仓 330 件

## Appendix: Design Process Notes

> 以下内容来自设计讨论中的观察，保留作为过程记录，非实现规格。

### What I noticed about how you think

- 你最初问了"一个 agent 还是多个 agent"，但当第二意见挑战"先单后多"的前提、指出读写安全边界时，你立刻接受了并修正了方向。这种面对新证据时快速调整的能力，比坚持原始方案稀缺得多。
- 你对自己要嵌入的系统有清晰认知——PC 端 + 微信小程序端、Linux/Docker 部署——这些约束在对话一开始就抛出来了，说明你在想的是"怎么落地"而不是"怎么炫技"。
- 你从"六个能力必须一起交付"到"同意渐进式、先做最小闭环"的转变很关键。需求范围从六个功能收缩到一个楔子，这是从 builder 思维到 product 思维的跳跃。
- 你选择方案 B（理想架构）而非方案 A（最小可行），说明你对安全和审计有真实的关切——在企业内部系统中，这是对的。
