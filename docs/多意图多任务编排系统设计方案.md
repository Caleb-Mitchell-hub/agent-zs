# 多意图多任务编排系统设计方案

## 1. 背景与目标

企业级 Agent 应用中，用户的一条 query 经常包含多个意图/任务，且任务之间可能存在依赖、并行、条件分支关系（如"查权限再报销"、"查天气+订票+订酒店，跨周末再推荐景点"）。

如果每个业务场景都单独写一套处理逻辑，会导致：
- 代码不可复用，新场景接入成本高
- 容错、重试、超时逻辑分散，难以统一治理
- 难以监控和调试（哪个子任务慢/失败说不清）

**设计目标**：抽象出一套与具体业务无关的通用编排框架，业务方只需注册工具（Tool）和补充 few-shot 示例，即可复用全部编排、容错、可观测能力。

---

## 2. 整体架构

```
┌───────────────────────────────────────────────────┐
│                  1. API Gateway 层                  │  接收用户请求，鉴权、限流
├───────────────────────────────────────────────────┤
│              2. Intent & Slot Layer                 │  意图理解，槽位提取，信息补全
├───────────────────────────────────────────────────┤
│                3. Planning Layer                     │  LLM 生成任务 DAG
├───────────────────────────────────────────────────┤
│                4. Tool Registry                      │  统一工具/API 定义与元信息
├───────────────────────────────────────────────────┤
│              5. Execution Engine                     │  DAG 调度：并行/串行/条件/重试
├───────────────────────────────────────────────────┤
│              6. Aggregation Layer                    │  结果校验 + 语义融合生成回复
├───────────────────────────────────────────────────┤
│              7. Observability 层                     │  贯穿全链路：日志/追踪/指标
└───────────────────────────────────────────────────┘
```

各层职责单一、可独立测试、可独立扩展，是整套方案能复用的核心前提。

## 3. 模块详细设计

### 3.1 Intent & Slot Layer（意图理解层）

**职责**：判断 query 是单意图还是多意图，提取关键槽位，识别缺失信息。

```python
class SlotExtractionResult:
    is_multi_intent: bool
    raw_query: str
    extracted_slots: dict          # 已提取的槽位，如 {"city": "上海"}
    missing_required_slots: list   # 缺失但必需的槽位，如 ["trip_duration"]
    clarification_question: str | None  # 需要追问时的话术
```

**关键设计点**：
- 用轻量分类器（小模型或规则）先判断"是否多意图"，避免所有请求都走重量级 Planning，控制成本延迟。
- 缺失必需槽位时，直接返回追问，不进入 Planning 阶段，避免生成一个执行不了的 DAG。

---

### 3.2 Planning Layer（任务规划层）

**职责**：基于 Tool Registry 中已注册的工具列表，让 LLM 生成结构化任务依赖图（DAG）。

```python
PLANNING_PROMPT = """
你是任务规划器。基于用户请求和可用工具列表，生成任务依赖图。

可用工具：
{tool_registry.list_tools_with_schema()}

用户请求：{user_query}
已提取槽位：{extracted_slots}

规则：
1. 无依赖关系的任务并行执行（放入同一批次）
2. 有依赖的任务需声明 depends_on，并用 {{task_id.field}} 引用前置任务结果
3. 需要条件判断的任务需声明 condition 字段
4. 涉及资损操作（下单/支付/提交审批）的任务需声明 requires_confirmation: true

只输出如下 JSON，不要任何其他文字：
{{
  "tasks": [
    {{
      "id": "task_1",
      "tool": "工具名",
      "params": {{...}},
      "depends_on": [],
      "condition": null,
      "requires_confirmation": false
    }}
  ]
}}
"""
```

**关键设计点**：
- Planning 层只负责"生成计划"，不负责"执行"，两者严格解耦，方便单独做计划的人工审核/回放调试。
- Prompt 里的工具列表是**动态注入**的，不同业务场景注册不同工具，Planner 代码本身不用改。
- 建议对 Planner 的输出做一次 JSON Schema 校验，非法结构直接打回重试，不要让脏 DAG 进入执行阶段。

---

### 3.3 Tool Registry（工具注册层）

**职责**：所有工具（查天气、查权限、订机票、生成文档……）用统一 schema 描述，是整套框架可复用性的核心基础设施。

```python
from dataclasses import dataclass
from enum import Enum

class FallbackStrategy(Enum):
    SKIP = "skip"       # 失败可跳过，不影响主流程（如查天气）
    RETRY = "retry"     # 失败重试
    BLOCK = "block"     # 失败必须终止全流程（如查权限）

@dataclass
class ToolSpec:
    name: str
    description: str
    input_schema: dict
    output_schema: dict
    is_idempotent: bool          # 是否可安全重试（订票/支付类为 False）
    timeout_ms: int
    fallback_strategy: FallbackStrategy
    requires_confirmation: bool = False   # 是否需要用户二次确认

class ToolRegistry:
    def __init__(self):
        self._tools: dict[str, ToolSpec] = {}

    def register(self, spec: ToolSpec, handler):
        self._tools[spec.name] = (spec, handler)

    def get(self, name: str) -> ToolSpec:
        return self._tools[name][0]

    def list_tools_with_schema(self) -> str:
        # 供 Planning 层拼接进 prompt
        return "\n".join(
            f"- {s.name}: {s.description}, 入参: {s.input_schema}, 出参: {s.output_schema}"
            for s, _ in self._tools.values()
        )
```

**新场景接入示例**（无需改动任何编排代码）：

```python
registry.register(
    ToolSpec(
        name="query_user_permission",
        description="查询当前用户的报销权限等级",
        input_schema={"user_id": "str"},
        output_schema={"level": "str", "limit_per_night": "number"},
        is_idempotent=True,
        timeout_ms=2000,
        fallback_strategy=FallbackStrategy.BLOCK,  # 权限查不到，绝不能瞎生成报销单
    ),
    handler=query_permission_api,
)
```

### 3.4 Execution Engine（执行引擎）

**职责**：通用 DAG 调度器，不感知具体业务，只处理"依赖关系 + 并行 + 条件分支 + 容错"。

```python
import asyncio

class DAGExecutor:
    def __init__(self, registry: ToolRegistry):
        self.registry = registry

    async def execute(self, task_graph: list[dict], on_task_complete=None):
        results: dict[str, any] = {}
        pending = list(task_graph)

        while pending:
            ready = [t for t in pending if self._deps_satisfied(t, results)]
            if not ready:
                raise RuntimeError("检测到循环依赖或死锁")

            batch_results = await asyncio.gather(
                *[self._execute_one(t, results) for t in ready],
                return_exceptions=True,
            )

            for task, result in zip(ready, batch_results):
                if isinstance(result, Exception):
                    result = self._handle_failure(task, result)
                results[task["id"]] = result
                if on_task_complete:
                    on_task_complete(task["id"], result)   # 支持流式回调，前端可逐步渲染
                pending.remove(task)

        return results

    def _deps_satisfied(self, task, results):
        return all(dep in results for dep in task.get("depends_on", []))

    async def _execute_one(self, task, prior_results):
        # 条件分支判断
        if task.get("condition") and not self._eval_condition(task["condition"], prior_results):
            return {"skipped": True, "reason": "condition_not_met"}

        spec = self.registry.get(task["tool"])
        params = self._resolve_refs(task["params"], prior_results)

        if spec.requires_confirmation:
            return {"pending_confirmation": True, "task": task}  # 交还给上层等待用户确认

        return await asyncio.wait_for(
            self._call_tool(spec, params), timeout=spec.timeout_ms / 1000
        )

    def _handle_failure(self, task, error):
        spec = self.registry.get(task["tool"])
        if spec.fallback_strategy == FallbackStrategy.BLOCK:
            raise error   # 阻断型失败，终止整个 DAG
        return {"error": str(error), "skipped": True}   # 降级型失败，跳过继续

    def _resolve_refs(self, params, results):
```

**关键设计点**：
- **容错分级**：`BLOCK` / `RETRY` / `SKIP` 三级策略在 ToolSpec 里声明，Executor 统一按声明处理，业务方不用每次都写 try-catch。
- **需要用户确认的操作**（下单、提交审批）不在 Executor 内部自动执行，而是返回 `pending_confirmation` 状态，交还上层等待用户点击确认后再继续——这是资损防护的关键设计。
- **流式回调** `on_task_complete`：天气查完就先展示，不用等机票查完，提升体验。
- 条件表达式不要用 Python 原生 `eval()`（有代码注入风险），建议用 `simpleeval` 等受限求值库。

### 3.5 Aggregation Layer（结果整合层）

**职责**：把所有子任务结果（含跳过/失败的）融合成一段自然、有逻辑的回复，而不是简单拼接。

```python
AGGREGATION_PROMPT = """
以下是各任务的执行结果，请融合成一段自然、有逻辑的回复。

规则：
- 被跳过的任务不要提及跳过原因，除非用户明确关心
- 失败的任务需要委婉说明，并给出替代建议
- 有因果关系的信息要联动表达（如天气影响穿衣/出行建议）
- 需要用户确认的操作，要明确告知用户下一步该做什么

任务结果：{json.dumps(results, ensure_ascii=False)}
用户原始请求：{user_query}
"""
```

### 3.6 Observability（可观测性）

贯穿全链路，不是可选项：

| 埋点位置 | 记录内容 |
|---|---|
| Planning 层 | 生成的 DAG、耗时、是否命中 JSON 校验失败重试 |
| 每个 Task 执行 | 工具名、入参（脱敏）、耗时、成功/失败/跳过、重试次数 |
| Execution Engine | 整体 DAG 耗时、关键路径（哪个任务拖慢了总时长）|
| Aggregation 层 | 融合耗时、最终回复长度 |

建议用 OpenTelemetry 之类的标准方案打点，每次请求生成一个 `trace_id`，贯穿 Planning → Execution → Aggregation 全程，方便排查"这次响应为什么慢/为什么答案不对"。

## 4. 端到端流程示例

以"上海出差规划"为例，串联各层：

```python
async def handle_user_query(user_query: str, user_id: str):
    # 1. 意图理解 + 槽位提取
    slot_result = await intent_layer.extract(user_query)
    if slot_result.missing_required_slots:
        return ask_clarification(slot_result.clarification_question)

    # 2. Planning：生成 DAG
    task_graph = await planner.generate_dag(user_query, slot_result.extracted_slots, tool_registry)

    # 3. Execution：调度执行（支持流式回调）
    results = await dag_executor.execute(
        task_graph,
        on_task_complete=lambda tid, r: stream_to_client(tid, r)
    )

    # 4. 校验是否有需要用户确认的操作
    pending = [r for r in results.values() if isinstance(r, dict) and r.get("pending_confirmation")]
    if pending:
        return ask_user_confirmation(pending)

    # 5. Aggregation：语义融合
    final_reply = await aggregator.merge(results, user_query)
    return final_reply
```

## 5. 新场景接入成本（体现方案价值）

以本文讨论过的三个场景为例，接入新场景只需要：

| 场景 | 需要新增的工具 | 需要改动的编排代码 |
|---|---|---|
| 查权限报销 | `query_user_permission`, `generate_expense_report` | 无 |
| 上海出差规划 | `query_weather`, `search_flights`, `search_hotels`, `recommend_attractions` | 无 |
| 未来新场景 X | 若干新 ToolSpec | 无（Planner 会自动感知新工具） |

编排代码只在以下情况才需要改：
- 新增一种全新的容错策略类型
- 新增一种全新的分支逻辑原语（目前的 `condition` 表达式覆盖不了）

## 6. 关键风险与应对

| 风险 | 应对 |
|---|---|
| Planner 生成非法 DAG（字段缺失/循环依赖）| JSON Schema 强校验 + 拓扑排序前先做环检测，失败则重新规划（最多重试 2 次）|
| 资损操作被自动执行 | `requires_confirmation` 强制走人工确认节点，Executor 层面硬编码不允许绕过 |
| 工具超时拖慢整体响应 | 每个 ToolSpec 声明独立 timeout，超时后按 fallback_strategy 处理，不拖累其他并行任务 |
| 幻觉：LLM 编造工具没返回的数据 | Aggregation 阶段的 prompt 明确要求"只基于任务结果作答"，并对高风险场景（如金额、权限）做二次校验规则 |
| 缓存/重复调用浪费成本 | 同一会话内相同参数的幂等工具调用可加缓存层（如 Redis，TTL 按数据时效性设置）|

---

## 7. 技术选型建议

- **DAG 调度**：Python 可基于 `asyncio` 自研（如上），或用 Prefect / Temporal 等成熟工作流引擎（更适合任务重、需要持久化状态的场景）
- **条件表达式求值**：`simpleeval`（避免裸 `eval`）
- **JSON Schema 校验**：`pydantic` / `jsonschema`
- **可观测性**：OpenTelemetry + 自建 trace 看板，或直接接现有 APM（Datadog / SkyWalking）
- **Planning 用的模型**：结构化输出场景建议用支持 function calling / JSON mode 的模型，减少解析失败率

---

## 8. 后续可扩展方向

- **多轮修正**：用户对某个子任务结果不满意（如"换个近地铁的酒店"），支持只重新执行该子任务，不用整个 DAG 重跑
- **计划回放与人工审核**：把 Planning 生成的 DAG 落库，支持离线回放和人工标注，用于持续优化 Planner 的 few-shot 示例
- **多 Agent 协作**：当某个 Task 本身足够复杂（如"生成报销单"涉及多步文档操作），可以把该 Task 升级为一个子 Agent，对上层 Executor 仍暴露统一的 Tool 接口
